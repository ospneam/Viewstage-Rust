# 笔迹缓存增量绘制（第九轮）

> 目标：静态笔迹层不再"每次全量重传"，改成**驻留式缓冲 + 绘制期剔除**。

## 结论：平移期间静态层上传从"周期性尖峰"变为恒零

## 旧设计的真实代价

旧静态层的 GPU 缓冲**只装当前可见的段**，用"缓存矩形比视口每边外扩 25%"
（`CULL_MARGIN_RATIO = 0.25`）做迟滞，避免小幅平移就重建。问题在于这个
迟滞本身就是重建频率的来源：

```
视口宽 1920px → 缓存矩形只大 480px/边
→ 每平移 480px，全量重新打包 + 重传一次
```

更糟的是 `upload_static` 的增量路径要求 `slot.cache_view == view_rect`
（视口**位级一致**），所以只要视口动过，晾干一笔也只能走全量重传。

实测代价（每笔 40 段 = 2.5 KB，笔迹密集分布在视野内）：

| 视野内笔迹 | 一次整表重写 | 平移 1000px | 平移 4000px | 新设计 |
| --- | --- | --- | --- | --- |
| 50 笔 | 125 KB | 3 次 · 352 KB | 9 次 · 475 KB | **0** |
| 150 笔 | 375 KB | 3 次 · 1070 KB | 9 次 · 1465 KB | **0** |
| 400 笔 | 1000 KB | 3 次 · 2860 KB | 9 次 · 3932 KB | **0** |

注意形态：不是"每帧都贵"，而是**每 480px 一次几百 KB ~ 1 MB 的上传尖峰**，
正好砸在平移手势中间——这正是"手感发顿"而非"帧率偏低"的来源。

## 新设计：把"驻留"和"可见"解耦

| | 决定什么 | 变化时机 |
| --- | --- | --- |
| **驻留**（缓冲里有什么） | 只由**笔画集合**决定 | 书写追加（偏移增量）/ 橡皮擦·undo（整表重传） |
| **可见**（本帧画哪些） | 每帧按笔画 AABB 算 | 每帧（平移/缩放/窗口尺寸） |

可见性算出的不是"上传什么"，而是**绘制实例区间**：

```rust
draw(0..6, start..start + len)   // 每个可见连续游程一次
```

**着色器零改动**。`@builtin(instance_index)` 按 WebGPU 规范本就包含
`firstInstance` 偏移，所以 `segments[instance_index]`（VS 与 FS 各一处）
在 `draw(0..6, start..end)` 下天然取到正确的段。DX12 上对应
`D3D12_DRAW_INDEXED_INSTANCED` 的 `StartInstanceLocation`，语义一致。

### 关键细节：相邻可见笔画合并

段在缓冲里按笔画顺序连续排列，所以连续的可见笔画本来就是一段连续区间，
直接并成**一次** draw。实测密集笔迹下 400 笔可见 → **1 批**（不是 400 批）。

只有交错可见（大量零散标记）才会拆开。为把最坏情况钉死，加了
`MAX_STATIC_DRAWS = 64`：区间数超上限就退回单次全量 draw。退化的只是剔除
收益，**不会**退回"重新上传"——缓冲照样驻留，所以最坏情况是"多算点顶点"，
而不是"重新花几百 KB 传一遍"。

## 状态机（已逐状态模拟验证）

```
                  快照未变（含平移）
              ┌──────────────────────────┐
              ▼                          │
        [驻留缓冲] ── 前缀追加 ──▶ 偏移增量写 ──┘
              │                            ▲
              └── 橡皮擦/undo/缓冲重建 ──▶ 整表重传
```

不变量（模拟全部通过）：

1. `sum(ranges.len()) == seg_count == persisted_segs`
2. `ranges.len() == snapshot.len()`，且第 i 项精确对应 `snapshot[i]`
3. 区间首尾相接、升序、无空洞
4. **绑定组永远指向当前缓冲**——缓冲重建后必须 `refresh_bind_group`，否则
   绑定组会指向已释放的旧缓冲（这是本轮特意设防的失效模式）
5. `capacity >= seg_count * 64`

| 转换 | incremental | rebuilt |
| --- | --- | --- |
| 首帧 | 否 | 是 |
| 平移（快照未变） | **提前返回，零上传** | — |
| 追加一笔（容量够） | 是 | 否 |
| 追加一笔（触发扩容） | **否（降级整表）** | 是 |
| undo 改中段 / 橡皮擦 | 否 | 视容量 |

第 4 行是关键：增量路径的前缀在缓冲换新后已失效，若不降级就会把段写进新
缓冲的空白区（画面丢笔）。实现里 `incremental = appendable && !rebuilt`。

## 顺带删掉的死代码

剔除从"上传期"移到"绘制期"后，这几个东西彻底没人用了：

- `CULL_MARGIN_RATIO`（旧迟滞旋钮本身）
- `expand_rect` / `rect_contains`
- `collect_static_segs`（旧"只打包可见段"路径）
- `StaticUploadSlot` 的 `culled` / `cache_rect` / `cache_view` 三个字段

全仓死符号扫描已清零；`crates/viewgfx/tests/perf.rs` 的两个基准改为走新的
`cull_visible`，其结论也一并更正（原先写"优化后恒为 1 批"）。

## 代价：显存（必须明说）

驻留意味着缓冲按**整份文档**增长而非当前视野：

```
10 万段 × 64 B ≈ 6.4 MB
```

对任何近代 GPU 都是可忽略量级，而它换来的是平移零上传。但这是本设计**最需要
被知晓的取舍，不是纯粹的免费午餐**——如果未来出现十万级段的大文档场景，
应该重新评估（届时的正确方向是分块驻留 + 按块区间 draw，而不是回到
"平移重传"）。

HUD 已把这条暴露出来（开发者模式）：

```
静态可见 150/500
驻留 20000 段 1.2 MB | 绘制 1 批
```

`驻留` 是显存占用的直接度量，`绘制 N 批` 是分批开销，两者一起看才能判断
"剔除 + 分批"这笔交易划不划算。

## 测试

新增 8 个针对 `cull_visible` 的纯函数测试（无 GPU 依赖）：

| 测试 | 锁定的不变量 |
| --- | --- |
| `without_rect_draws_everything` | 视口未知 → 不剔除，单区间覆盖全部 |
| `coalesces_contiguous_strokes` | 连续可见 → 合并为一次 draw |
| `splits_on_offscreen_stroke` | 中间笔不可见 → 区间正确断开 |
| `all_offscreen_yields_zero_draws` | 全移出视野 → 零 draw |
| `skips_empty_strokes_without_breaking_coalescing` | 0 段笔画既不计入可见、也不该断开区间 |
| `falls_back_to_single_draw_past_the_cap` | 超 `MAX_STATIC_DRAWS` → 退化为单批，统计仍按真实可见集 |
| `ranges_shorter_than_snapshot_is_safe` | 长度不一致按 zip 配对，不越界 |
| `empty_input_is_noop` | 复用缓冲必须先清空，不能残留幽灵绘制 |

删除 3 个（`collect_static_segs` ×2、`rect_contains_and_expand_agree`）——
被测函数已不存在。另有 1 个 `static_resident` 统计往返测试。

## 验证方式

本机无 `cargo`/`rustc`，未经编译验证。已做：

- 括号平衡（全仓，含剥离字符串/注释）
- 上传状态机逐转换模拟（9 个转换，含扩容降级、undo 缩表、清空全部）
- `upload_static` 签名与调用点匹配
- 死符号全仓扫描（旧剔除辅助 4 个符号清零）
- HUD `format!` 占位符/实参计数配平（14/14）

Windows 上请确认：

1. `cargo build --release` 通过；
2. **平移时 `[rstat]` 的静态上传字节应不再增长**（HUD 的"驻留/绘制"行可见）；
3. **撤销、橡皮擦之后笔迹完整无缺**——这是本改动最危险的失效模式
   （前缀失效会静默丢笔，画面上表现为局部笔迹消失）；
4. 大幅平移到完全空白区域 → 笔迹应消失（不是残留）；
5. 平移回原位 → 笔迹完整恢复；
6. 缩放时笔迹边缘无缺失（AABB 剔除用的是含半宽外扩的包围盒）。

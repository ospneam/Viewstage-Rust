
## P0 DComp 互操作 spike：根因突破 + GO 确认（2026-10-01）

**根因（数日二分的最终答案）**：`IDCompositionTarget` / `IDCompositionVisual` 的 COM 引用必须在窗口生命周期内保活。spike 的 `setup_dcomp` 函数返回后局部 target/root 被 Drop → DComp target 对象销毁 → visual 树与 HWND 绑定拆除 → 窗口显示 DWM 默认白色。C++ 版成功、Rust 版失败的差异不在 API/依赖/wgpu/windows-rs，纯粹是 COM 生命周期。

**二分路径**（可复用方法论）：建独立无 wgpu 最小 crate（dcomp-rs-min）建立"Rust 也能行"基线 → 代码整体替换进 spike 依赖环境（排除依赖层）→ 逐函数搬回（窗口/设备/swapchain OK）→ 锁定 setup_dcomp → 内联 vs 函数对照（H/I）→ 三元组保活验证（J）全通过。

**验证结果**：spike-dcomp D3D11 模式与 wgpu 默认模式（DX12 后端、backbuffer 导入、CopyResource→Present1→Commit）均 PASS，9/9 网格探针点颜色正确。

**P0 判定：GO**。DXGI composition swapchain → DComp visual → 上屏链路本机可用。

**P1 设计约束（必须遵守）**：DComp 集成层（未来 viewcomp 或等价模块）必须持有 target/visual 的 COM 引用直到窗口销毁；DComp 设备创建：D3D12 queue 路线在本机 E_NOINTERFACE（v2/v3 都不行），用 IDXGIDevice 路线或 null rendering device（两者实测均可合成）。

**其他实测事实**：wgpu 27 静态链接不影响 DComp；windows-rs 0.58 封装无坑；v1 CPU surface 本机 dcomp.dll 有缺陷（EndDraw segfault），更新 surface 走 D2D v2 路线；Present1 必须传 DXGI_PRESENT_PARAMETERS 默认结构体（nullptr AV）。

## P1 DComp 基础设施 crate viewcomp 完成（2026-10-01）

**新增 `crates/viewcomp`**（P1 交付物，未接主程序——P2 再接线）：
- `DcompCompositor`：设备（IDXGIDevice 路线）+ target + root visual 全引用持有（保活契约），add_visual_on_top/above（z-order）、set_content_swapchain/raw、set_offset（cast IDCompositionVisual2 → SetOffsetX2/Y2）、commit/wait_for_commit、destroy()。Drop 语义：释放 target 引用即解绑（windows 0.58 无 DestroyTarget 生成）。
- `create_composition_swapchain(device: &IUnknown, size, SwapchainDesc)`：FLIP_SEQUENTIAL+PREMULTIPLIED+B8G8R8A8 双缓冲默认，device 收 D3D12 queue 或 D3D11 device 的 IUnknown。NV12（P3 媒体链）参数化预留。
- `present_one()`：硬约束 #3 封装（Present1 非空 params；windows-rs 0.58 中 Present1 返回 HRESULT 需 .ok()）。
- `tests/smoke.rs`：真实窗口全链路冒烟（10 步全过，384x261）。

**windows-rs 0.58 实测 API 陷阱**（均已写入代码注释）：
1. WNDCLASSEXW/RegisterClassExW 需要 `Win32_Graphics_Gdi` feature（不在 WindowsAndMessaging）。
2. CreateWindowExW 时窗口类必须设 lpfnWndProc——null proc 在 WM_NCCREATE 即 fail-fast（STATUS_STACK_BUFFER_OVERRUN）。
3. AddVisual 的可空 BOOL* insertAbove 生成为非空 Param<BOOL>——用 BOOL(1)+reference 表达插顶，z-order 上屏复核后可能需改 BOOL(0)。
4. IDCompositionVisual 的静态偏移是 IDCompositionVisual2::SetOffsetX2/Y2（SetOffsetX 只收动画）。

**回归**：workspace 28 个测试套件全绿。
**下一步 P2**：iced_winit Compositor fork 接管主视觉（VIEWSTAGE_DCOMP 门控，winit no_redirection_bitmap 窗口属性 + wgpu raw queue → viewcomp swapchain）。

## icon 清晰度调查（用户报告 DComp 路径 icon 变糊）——取证未复现

**方法**：给两条路径都加了后缓冲读回探针（`VIEWSTAGE_DCOMP_READBACK=N` / `VIEWSTAGE_LEGACY_READBACK=N`，dump BMP 到 tmp-probe/），加上屏幕截图、分块锐度扫描、结构差异热图。

**证据链（全部通过）**：
1. DComp 后缓冲 == 屏幕截图（工具栏 lap_var 1675 vs 1676）——合成 1:1 无重采样；
2. legacy 后缓冲 == DComp 后缓冲（工具栏 1694 vs 1675 = 1.01x；全帧 480 块锐度零差异；icon 线条像素 1091=1091、亮度 229.0=229.0）；
3. 结构差异热图只亮在相机动态内容，UI 全黑（零差异）；
4. swapchain/client 在创建和三次 resize 全 MATCH，viewport 1920x1080 scale 1.250 正确；
5. 两路径 idle fps 相同（~15）。

**Chrome 对照**（gpu/ipc/service/direct_composition_child_surface_win.cc）：desc 逐字段与 viewcomp 一致（FLIP_SEQUENTIAL + PREMULTIPLIED + Scaling=STRETCH + 物理像素 + resize 走 ResizeBuffers）——没有可抄的缺失项。

**结论**：静态像素层面两路径无法区分；用户感知的差异需要具体复现状态（哪个 icon / 什么交互 / 是否多显示器）。探针代码保留（env 门控、取证可复用），COPY_SRC usage 为永久无害新增。

## 批注性能/延迟/GPU 优化（用户点名批注，实测驱动）
- 实测发现两个真 bug（书写会话 rstat + 注入书写 12s）：
  1. **upload_dynamic 增量路径失效**：append_only 条件要求 stable_fp 变化——稳定层不变的帧（书写时绝大多数帧）落入全量分支，每帧重打包整条笔画。实测动态上传随手写时长线性增长（28KB/s → 4.2MB/s）。修复：增加 stable_unchanged 分支（前缀已持久化，只写尾层）。修后恒定 ~46KB/s，与笔画长度无关（长笔画会话 ~90 倍削减，且不再恶化）。
  2. **静态瓦片 blit 默认关闭**：blit_enabled 用 `is_ok_and` ——env 未设置时 Err→false，与文档"默认开启、=0 退回"语义相反。静态笔迹一直走每帧全量几何重放（O(全部静态段)）。修复：`map_or(true, |v| v != "0")` 默认开启。修后收笔增量光栅化 15 瓦片、每帧 1 次 draw blit 内容瓦片（O(内容瓦片) 替代 O(全部静态段)）。
- 视觉验证（无相机 + 注入书写 + 后缓冲读回）：动态层（书写中）与静态层（收笔后 blit）渲染完整、AA 平滑、无缺失。注意：VIEWSTAGE_NO_CAMERA=1 时 idle 仍 30fps（cam_msg 继续驱动重绘，只是不传 NV12）。
- 触控延迟链审查结论：RawTouch* 在 process_touch_events 内同步递归处理（无额外消息跳）；剩余 hop 仅 hook→tokio→winit（1-3ms），不值得动。每事件尾层重建冗余 ~15×/帧 @1000Hz，实测 ~1-2μs/次，可忽略。
- 教训：MEMORY.md 里"批注已是终极形态勿动"结论有误——文档声称的增量行为与代码实际不符，实测才见真章。已修正记忆。

## 批注光标延迟专项（第四轮）
- 根因：笔/触控路径每个输入事件走「hook→notify→异步流→ProcessTouchBuffer 消息→App::update」，而 iced 运行时对每批消息**无条件 build_user_interfaces（全 widget 树重建+layout）**——笔事件 133-240Hz ⇒ 每秒数百次全树重建，帧预算被侵蚀成可见延迟。鼠标的零消息热路径从未覆盖笔/触控。
- 尝试并放弃：iced fork 加 is_view_invariant 跳过重建——不可行，UserInterface<'a> 与 program 生命周期绑定，旧 UI 存活期间无法 &mut program（E0502 结构性冲突）。fork 改动已全部回退。
- 最终方案（应用层零消息笔触路径）：
  - sys/touch.rs：hook（UI 线程）事件入队后直接 **InvalidateRect(hwnd)** 请求重绘（原 notify→异步 worker→消息 绕行删除；HWND 以 isize 存进 SHARED 避免裸指针非 Send）。
  - canvas::Program::update 新增 RedrawRequested 分支 → drain_touch_zero_msg：Down/Move 在渲染帧内直写共享状态（手势 RefCell、is_drawing Cell、pinch 锚 Cell、momentum RefCell 化），**不发布任何消息 ⇒ widget 树零重建**；draw 随后渲染最新笔迹，输入→像素一帧直达。
  - Up 的 finalize（&mut：undo 栈/mesh 缓存/Vec）延迟为 TouchFinalize 消息（每笔画一次，顺带同步 undo 按钮）；Up 截断后剩余事件留 pending 下帧处理保序。
  - raw_touch_worker/ProcessTouchBuffer/RawTouchStart/Move/End 消息删除；FrameTick 仅服务惯性（needs_frame_tick 只看 momentum）。
  - paced_redraw：is_drawing 时满 vsync 渲染（60fps cap 只留悬停/平移）。
- viewgfx：annotation_frame 的 trail 构建抽出为 update_touch_trail（消息路径/drain 共用）；DrainTouchHistory 类型别名清 clippy。
- 环境：bash 下 cargo 链接失败 = Git Bash 的 GNU link 抢占 MSVC link.exe + SDK LIB 缺失 ⇒ 用 tmp-probe/run_tests.bat（vcvars64）跑构建/测试。
- 验证：cargo check/clippy 零新增（顺手清 3 条预存告警）；workspace 132 测试全绿。
- 待真机验证：笔/触控书写观感（应显著跟手）、捏合/平移/undo 按钮回归。

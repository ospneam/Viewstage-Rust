## 批注静态笔迹瓦片光栅缓存（GPU 优化）

**背景**：全屏单纹理离屏光栅缓存（`VIEWSTAGE_STATIC_BLIT=1`，默认禁用）真机实测无收益。根因：桌面 GPU 上① 每笔晾干的 `load_op=Load` 增量 pass 是**整纹理带宽**操作（4K ≈ 33MB load+store/笔）；② draw 侧全屏 blit 采样，而笔迹屏幕覆盖有限。本次按 Chromium 模型瓦片化，两项成本均降为 ∝ 内容覆盖。

**实现**（viewink/src/render/annotation.rs + annotation_blit.wgsl + stats.rs）：
- 屏幕空间 256px 瓦片网格（`TILE_SIZE=256`），单张视口尺寸纹理 + 瓦片 scissor 维护（内存与旧全屏版相同）。
- `StaticRasterCache` 新增 `content_tiles: BTreeSet<(u32,u32)>`（含笔迹瓦片集）、blit 实例批（`Vec<[f32;4]>` NDC 矩形 + grow-only VERTEX 缓冲，`sync_blit_batch` 指纹门控上传）。
- `raster_decision` 状态机原样保留（UpToDate/Defer/MarkEmpty/Raster）；`Raster{full:false}` 从单 Load pass 改为**逐脏瓦片 pass**（scissor+Load，带宽 ∝ 脏瓦片数，每笔晾干 1~4 瓦片 ≈ 1MB）。
- 覆盖集来源 = **快照笔画 AABB**（构建时算好），不遍历段：全量重建 `rebuild_content_tiles`；增量并 `appended_from` 起的新增笔画瓦片（StaticUploadSlot 新增 `appended_from` 字段，增量上传=prev_len，全量=0）。
- blit shader 改 instanced：每实例瓦片 NDC 矩形（CPU 预计算含 y 翻转），UV 由片元坐标/纹理尺寸推导（1:1 零重采样模糊）。
- 覆盖集过滤矩形用 **slot 构建时的剔除矩形**（`slot.culled`+`slot.cache_rect`）而非当前视口——小幅 pan 后 upload 零工作复用，GPU 段集是旧可见集，覆盖集必须与段集同源（自查发现的 bug，已修）。
- `blit_enabled()` 默认**启用**；`VIEWSTAGE_STATIC_BLIT=0` 退回几何重放做 A/B。
- 瓦片覆盖计算外扩 `TILE_AA_PAD_PX=2`（防跨瓦片 AA 拼缝被 scissor 裁掉）。
- stats 新增 `ink_tiles content=N blit=N pass=N up=N`（观测点：blit 应远小于全屏瓦片数 4K≈128；pass 每笔 1~4）。
- 净删代码：全屏 blit 全屏三角版退役；净增 ~200 行。

**关键映射**：`CanvasToPixel{s,ox,oy}`：`px = (canvas×scale+offset)×scale_factor`，与 `ViewTransform::to_matrix` 链一致（无旋转，AABB 变换安全）。

**测试**：viewink 26 项全绿（新增 6 项：CanvasToPixel 映射、tile_grid、px_rect_to_tiles 边界/剔除、tile_ndc_rect y 翻转/clamp、rebuild_content_tiles 剔除、增量并入）。

**真机观测点**（debug 版 + `[rstat]` 日志）：
- 静止时 `anno_draw static=1 binds=1`，`ink_tiles blit=N`（N=内容瓦片数，应远小于全屏数）；
- 书写晾干每笔 `raster_incr=1 pass=1~4`；
- pan/zoom 中 `anno_draw static=1`（几何重放降级），停稳后一次 `raster_full=1`。
- A/B：`VIEWSTAGE_STATIC_BLIT=0` 对比几何重放路径的 GPU 占用。

## 摄像头 GPU 渲染优化

**成本盘点**（camera.rs 全文 + camera.wgsl + padded_plane.rs）：管线已精简（NV12 直传、generation 门控上传、cached uniform/quad、相机帧无 mip、BgKey dirty-cache 参数层）。剩余四项确定性成本：

1. **混合 dst 读**：camera 双管线用 ALPHA_BLENDING，但 FS 恒 alpha=1 且画在不透明 backdrop 上 → 混合等价直写，硬件却每像素读 dst（+4B）。**修复**：NV12 管线改 REPLACE（省 ~400MB/s dst 读 @1080p60）；RGBA 图片管线**保持 ALPHA**（透明 PNG 的 col.a<1 需要混合——自查发现的语义陷阱）。
2. **identity 滤镜 ALU**：默认滤镜 [0,1,0] 下 apply_filter 恒等映射但每像素照跑 ~10 ALU。**修复**：shader 开头 uniform 一致分支旁路（App 侧 0/100 构造位级精确；非默认自然回退）→ 省 ~1G ALU/s。
3. **上传 padding memset**：staging 逐帧 clear+resize(0) 整块清零，但 copy_buffer_to_texture 只读每行前 width_bytes 字节、padding 不被读 → 改为仅扩容时清零（1080p NV12 省 ~150MB/s CPU memset）。顺带修了 write_buffer 传整块 Vec（含历史多余字节）的隐患（现在精确传 staged_len）。
4. **双平面双 submit**：NV12 Y+UV 各自 encoder+submit → PaddedPlaneUploader 拆 `upload_into`（外部 encoder）+ NV12 两处调用点合并单 submit（30fps 时 60→30 submit/s）。旧 `upload` 接口保留为单平面便捷入口（RGBA 图片路径用）。

**评估后不做的**：YUV→RGB 转换结果离屏缓存（draw 读 RGBA 400MB/s + 写 240MB/s，换 ALU 减半——核显带宽敏感，负优化）；wgpu 原生 NV12 纹理格式（需 feature、跨平台兼容差）；滤镜矩阵系数 CPU 预计算（收益 4 ALU/px，不值得动共享 Globals 布局）；无新帧跳过 draw（直通合成每帧重画 frame，架构上不可跳）；**DWM 硬件 overlay 直通**（Chrome Windows 大杀器：DirectComposition video surface 绕过合成器、YUV 由显示引擎固定功能处理，3D 引擎零负载）——等价实现需给摄像头区域独立 swapchain/visual，与 iced/wgpu 单窗口单 surface 冲突（wgpu surface 走 CreateSwapChainForHwnd，DComp 需 CreateSwapChainForComposition + 自管 visual 树，wgpu 稳定 API 不暴露；子 HWND 双窗口方案：YUV 转换仍在同一 GPU 的 shader 里跑，零净节省，外加 z-order/输入穿透/每帧同步位置的新 jank 源）。且即便做成了，Chrome 自己在视频带滤镜/变换时也回退合成器——我们的 brightness/contrast 滤镜路径会强制 fallback。直通通道下摄像头已是"主 pass 里一个 quad"，剩余 overlay 级收益只剩固定功能 YUV 处理 ≈ 1~2ms/帧 3D 时间，架构不可达，记录归档。

**验证**：viewcamera check --all-targets 零代码警告；workspace 测试 + debug 构建进行中。

**第二轮（对标 Chromium 继续做）**：

5. **BT.601/709 矩阵分支化**：`fs_main_nv12` 的色彩矩阵系数从 `mix(bt601, bt709, k)×4` 改为 `if k == 1.0` 一致分支（k 由 CPU 位级精确构造 0.0/1.0，插值场景不存在，无发散代价）→ 每像素省 ~8 ALU（mix 4 次 + 选择），约 1G ALU/s @1080p60。
6. **RGBA 不透明扫描 + REPLACE 三管线**（对齐 Chromium 不透明 quad 走 `BlendMode::kNone`）：`SingleTextureGpu` 加 `opaque: bool`，新增 `scan_opaque(rgba)`（`chunks_exact(4).all(|px| px[3]==255)`），两条 upload 路径 generation 门控扫描（每代内容只扫一次）；`CameraPipeline` 增 `pipeline_rgba_replace`（REPLACE），draw 按 `t.opaque` 分流三管线（rgba=ALPHA / rgba_replace=REPLACE / nv12=REPLACE）。完全不透明图片（截图、照片类）省 dst 读 ~400MB/s。

**第三轮（上传路径挂 iced 主帧 encoder + StagingBelt，对标 Chromium 上传并入帧提交 + 映射 transfer buffer 单拷贝）**：

7. **上传并入主帧 submit**：fork `DirectChannel::prepare` 签名扩展（+`encoder: &mut CommandEncoder` +`belt: &mut StagingBelt`），调用点在 `Renderer::prepare` 内（encoder/belt 均在作用域）；摄像头上传不再自建 encoder+submit（NV12 每帧省 1 submit，图片首传+mip 再省 1）。
8. **映射暂存单次 CPU 拷贝**：`PaddedPlaneUploader` 重写——旧 Vec 重打包 + `write_buffer` 内部再拷贝（双拷贝 ~14MB/帧 @1080p NV12）改为行直接写进 `belt.allocate` 映射切片（单拷贝 ~7MB/帧，省 ~210MB/s CPU 内存流量 + ~0.5ms 主线程/帧）；`MipGenerator::generate` 同步改为记入帧 encoder。

**正确性论证（关键证据链）**：
- belt 稳态复用不依赖外部 poll：wgpu-core `queue_submit` 内部调 `maintain(last_submission)` + `closures.fire()`（queue.rs:238-250）→ recall 的 map_async 回调在**下一次 submit 时泵出**，chunk 稳态 2 组循环（iced 自身上传即此机制，多年生产验证）。
- **自查排雷**：mip 链曾被自己的改动破坏——`generate` 原本 prepare 期即时 submit，而上传拷贝改记帧 encoder 后，GPU 执行序变为 mips 先于上传（读空纹理）；修复 = mip blit 与上传记**同一 encoder**（encoder 内命令按序：上传→mip→采样）。
- belt 契约：切片须在 finish 后、recall 前提交——帧 encoder 由 Renderer present 统一 finish→submit→recall（screenshot 路径同样经 draw()，一致）；映射视图在 finish 前丢弃；copy offset 由 allocate 512 对齐（校验仅要求 4 字节 COPY_BUFFER_ALIGNMENT）。
- fork 签名变更接线点：viewink `AnnotationLayer`（不使用，透传）、viewcamera `CameraChannel`（全用）+ `BackdropChannel`（静态纯色不用）、fork 测试 `RedChannel`。

**改动文件**：`iced-fork/iced_wgpu-0.14.0/src/direct.rs`（trait + 文档）、`src/lib.rs`（调用点）、`tests/direct.rs`、`crates/viewink/src/render/annotation.rs`（签名）、`crates/viewcamera/src/render/camera.rs`（上传链全接线，queue 死参数清除）、`crates/viewcamera/src/render/padded_plane.rs`（重写为 belt 单拷贝版）。

**第三轮后追加：DComp overlay 路线决策与方案（用户拍板做全量重写）**

核查结论（已与用户对齐）：Chrome 的 video deposits-to-overlay 需要拥有整棵 DComp 树；我们的 HWND 组合树归 DXGI 翻转交换链，公开 API 无法插入兄弟视觉 → 必须弃用 wgpu::Surface 重写 present；相机帧源是 nokhwa/msmf CPU NV12，overlay 省不了上传，仅省应用内 YUV→RGB（≈1-2% 带宽）；DWM 侧现有 independent flip 已是零重组。ROI 倒挂但用户拍板执行。

已验证的实施前提：
- wgpu-hal d3d12 互操作三件套齐备：`raw_device()` / `raw_queue()`（present_queue）/ `unsafe texture_from_raw()` / `buffer_from_raw()`（wgpu-hal 27.0.4 src/dx12/device.rs:430-455）。
- winit 支持 `no_redirection_bitmap` 平台属性（0.30.13，注意与 transparent 属性联动检查 window.rs:1232）。
- DX12 后端钉定无需改 fork：`WGPU_BACKEND=dx12`（iced_wgpu lib.rs:1311 `Backends::from_env().unwrap_or(PRIMARY)`）。
- DXGI NV12 composition 交换链 = Windows 媒体 overlay 标准机制（Haswell+ iGPU 支持硬件 NV12 平面）。

目标架构：HWND(NOREDIRECTIONBITMAP) → DComp 树：纯色视觉（画布底色，零 GPU）+ NV12 媒体交换链视觉（相机 30fps present，DWM 自动提升硬件 overlay）+ UI 合成交换链视觉（批注+iced UI，60fps，premultiplied alpha）。

分阶段：P0 互操作 spike（GO/NO-GO 门）→ P1 DComp 基础设施（VIEWSTAGE_DCOMP 门控）→ P2 主视觉接管（iced_winit Compositor fork，内容等价旧路径）→ P3 相机 overlay（NV12 交换链 + D3D12 原生拷贝 + 共享 fence）→ P4 生命周期（resize/DPI/设备丢失/回退）→ P5 真机 A/B 收尾。全程旧路径保留回退。总量估 8~11 天。
关键风险：双交换链帧同步（批注 vs 相机 1 帧错位）、NV12 后缓冲需 D3D12 原生拷贝绕开 wgpu 验证、overlay 提升不保证（回退 DWM 合成仅收益缩水）。

**最终验证**：workspace 131 项测试全绿（含新增 `scan_opaque_detects_fully_opaque_and_translucent`）；debug 构建成功，全部 warning 为增量编译锁文件/目录噪音（os error 5），零代码警告。
